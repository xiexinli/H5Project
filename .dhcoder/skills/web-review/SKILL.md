# Review

本 skill 是通用评审工作流驱动。评审语义放在 `REVIEW.md`；本 skill 负责评审流程。

## 工作流

1. 确认评审范围：当前 diff、指定 commit、指定文件或指定目录/模块。
2. 先看改动代码，再做大范围仓库浏览。
3. 只按需扩展上下文：确认归属、生命周期、状态流、契约或回归风险。
4. 产出发现前，先读 `REVIEW.md` 与相关 `.dhcoder/rules/`。
5. 只输出高信号发现；不要把评审变成全仓审计。

diff 已定义入口时，不要从全仓漫游开始。

## 上下文扩展

以下情形需要扩展：

- 公开函数/组件 props/emit 契约变化
- 状态流、事件派发、订阅、生命周期变化
- 需要宿主布局或样式联动的改动
- 登录、支付、隐私、埋点等关键链路
- 公共工具、基类、共享组件

扩展时回答：

- 改变了什么行为
- 谁拥有并触发它
- 生命周期、异步、空安全、资源绑定是否仍成立
- 风险是本改动引入、触发还是明显放大

## 架构路由

若 diff 触及分层代码，判断前先读 `.dhcoder/rules/architecture.md`：

- `views/` 不得直接调用 axios 或拼接请求
- `api/`、`services/` 是唯一可发起请求的层
- `composables/`、`stores/` 不直接操作 DOM/组件内部
- `utils/`、`types/` 不依赖 Vue / Vant / DOM

## 评审清单

- 确认改动停留在声明的范围内。
- 每条发现锚定到具体文件、函数、符号或代码路径。
- 严重发现要有证据，不靠宽泛猜测。
- 需要类型/构建/测试证据时用 `web-verify`。
- 没有发现具体缺陷时，直接说明，不要凑发现。

## 验证升级

优先用能证明结论的最小检查：

- `git diff --check`
- `pnpm type-check`
- `pnpm lint`
- 相关单元测试 `pnpm test`
- 运行期/视觉行为无法从静态阅读证明时，写人工验证说明

证据缺失时说明缺口，不提高严重度。
